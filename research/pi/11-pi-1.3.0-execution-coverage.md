# Pi 1.3.0 — execution coverage and the no-fork boundary

Reviewed **2026-10-19**. Companion: [published API verification](10-pi-1.3.0-api-review.md).

## Decision

**A no-fork Loom adapter is feasible as a trusted orchestrator, not as an in-process security sandbox.** Pi has a shared gate for ordinary model-issued tools and `ctx.executeTool()` calls. It does **not** have a universal gate for every execution, a fail-closed output-redaction contract, a fail-closed settlement contract, or guaranteed cancellation of external effects. Those distinctions follow from the execution paths below, not merely from documentation. Upstream explicitly places the real boundary at OS/container/VM permissions. [tool-pipeline] [nested-dispatch] [result-runner] [boundary-runner] [security]

Scope: exact `v1.3.0` source, commit **`71023aec1546d6d677a65669c5665c0927ce0dd0`**, supplied checkout at `/tmp/opencode/loom-pi-1.3.0-review/pi-71023aec1546d6d677a65669c5665c0927ce0dd0`. All upstream links below are immutable commit links. Published-package probes used the existing isolated `probes/node_modules` installation of `@earendil-works/pi-coding-agent@1.3.0`; the parent supplied the SHA512-verified npm artifact. This investigation did not install anything, change Loom's pin, implement an adapter, or use model/API credentials.

Historical comparison: this note qualifies, rather than edits, `04-verification-gateway.md` and `05-security.md`. Their no-OS-boundary warning remains correct. “Every MCP call” means calls through registered Pi tools, not MCP startup/discovery or arbitrary extension clients. “Fail-safe errors” applies to pre-execution `tool_call` and `user_bash`, **not** `tool_result` or `agent_before_settle`. The nested 256-call/8-KiB/32-KiB limits are **audit-record limits**, not execution or result quotas. [mcp-startup] [mcp-runtime] [result-runner] [boundary-runner] [nested-record]

## 1. Execution-path inventory

| Entry path | Actual coverage and limit |
|---|---|
| Top-level built-in tools | All eight (`read`, `bash`, `powershell`, `edit`, `write`, `grep`, `find`, `ls`) use the same agent pipeline when invoked by the model: find implementation → `prepareArguments` → schema validation → `tool_call` → execute → `tool_result`. Unknown tools and invalid arguments return errors **before hooks**; blocked calls skip execution and result hooks. This is a gate on accepted calls, not a complete attempted-call audit stream. [builtins] [tool-pipeline] [tool-finalize] |
| Top-level custom/extension tools | Same pipeline, with extension context injected by a wrapper. But the wrapper's `.execute()` directly calls the definition; it is not itself a gate. A custom `prepareArguments` also executes **before** `tool_call`, and extension/loadout code runs outside this call gate. Trust these implementations, not just their schemas. [tool-pipeline] [wrapper] [loadout] |
| Nested `ctx.executeTool()` | Re-enters `runToolCall` with the session's before/after hooks and `parentToolCallId`. Callable set: active `direct` tools plus every registered `codemode`/`deferred` tool; not `model-only`/`hidden`. Context forwards the parent's signal by default, but an explicit signal **replaces**, rather than combines with, it. [nested-dispatch] [callability] [tool-context] |
| Codemode `tools.*` | Registered callable tools are bridged to `ctx.executeTool()`, including MCP tools. Codemode excludes itself and is `model-only`. QuickJS does not expose Node/filesystem/network/timers; this does not constrain what a permitted host tool can do. [codemode-tools] [codemode-definition] [sandbox-surface] |
| Codemode `models.*` | **Separate execution channel.** With the normal extension default `models: true`, classifiers/image generation call `ctx.modelRegistry` directly, not `ctx.executeTool()`. There is no per-model-call `tool_call`/`tool_result` gate. These calls get codemode detail rows/usage, not the nested-tool pipeline. The bridge removes catalog `headers` and resolves the requested provider/id against the registry, ignoring script-supplied endpoint/header overrides; that is useful credential routing, not Loom approval/budget enforcement. `createCodemodeExtension({models:false})` removes the channel without a fork. [codemode-default] [codemode-tools] [codemode-models] [codemode-catalog] |
| MCP direct tools | `createMcpToolDefinition()` supplies an ordinary Pi tool whose execute calls `client.callTool`; normal pipeline hooks therefore cover tool invocation. The adapter rechecks current enabled/hidden/tool availability at execution. [mcp-register] [mcp-tool] |
| MCP codemode/deferred tools | Same underlying definitions/pipeline. MCP `codemode` exposure maps to Pi `deferred`; tools can be called from codemode without first activating them. `tool_search` changes declarations, not authorization. Resource-list/read helpers are registered tools too. [mcp-exposure] [mcp-register] [tool-search] |
| Interactive `!`/`!!`, RPC `bash` | **Different gate:** caller emits `user_bash`; first valid `{operations}` or `{result}` wins. `undefined` from every handler means local fallback. Throwing or returning an invalid shape rejects; interactive mode explicitly refuses fallback after a hook error. `{block:true}` is not a valid `user_bash` result. These paths do not emit model-tool `tool_call`/`tool_result`. [user-bash-runner] [interactive-bash] [rpc-bash] |
| SDK `session.executeBash()` | **No `user_bash` dispatch inside the method.** It directly applies settings' command prefix and invokes supplied operations or local Bash, then records the result. A host that calls it directly bypasses the UI/RPC interception layer and the built-in tool's `spawnHook`. `!!` excludes output from model context; it is not an execution restriction. [sdk-bash] |
| Extension `pi.exec()` | Calls `execCommand()` directly: raw process spawn, no tool hooks, no `user_bash`, no Bash `spawnHook`. The signal is optional and is not automatically the session signal. [extension-exec] [exec-process] |
| Extension direct OS / direct tool execution | Module imports and factories execute in-process. Node filesystem/process/network APIs are available, and `ctx.tools` returns executable tool objects, not just descriptions. Calling a tool object's `.execute()` directly does not re-enter `runToolCall`. Likewise, SDK `getToolDefinition()` exposes the definition. These are concrete ways a **trusted-code extension** can bypass the common gate; this is not a QuickJS escape or an upstream privilege escalation. [extension-load] [tool-context] [callability] [wrapper] |
| Startup/reload resources | Resource discovery, package resolution, extension import/factory execution, context/prompt reads, model/auth configuration and MCP connection setup are **not model tool calls**. Install/import/connect policy must be fixed before these stages; adding a later `tool_call` handler cannot intercept them. [sdk-startup] [resources] [extension-load] [package-resolution] [mcp-startup] |

Inside the built-ins, `read`/`ls` perform file operations, `write`/`edit` perform queued mutations, and default `grep`/`find` directly spawn `rg`/`fd`; those subprocesses do not pass through Bash's `spawnHook`. `find` can instead use custom `glob` operations, whereas `grep` still spawns local `rg` with its supplied filesystem helpers. Paths resolve against cwd but accept absolute/expanded paths: cwd is not filesystem confinement. PowerShell uses the shared shell execution backend. [read-ops] [ls-ops] [write-cancel] [edit-cancel] [grep-ops] [find-ops] [path-resolution] [powershell-backend]

Managed-helper acquisition is another execution path: `ensureTool` can download missing `rg`/`fd`, and extraction directly spawns system archive utilities. Interactive startup calls it for both helpers before rebinding extensions, independently of model-tool hooks. Preprovision/disable downloads in an owned environment rather than assuming a shell/tool gate observes them. This is source-only evidence; no helper download or extraction was triggered by the probes. [helper-acquisition] [helper-extraction] [interactive-helpers]

### Loadout is not an authorization boundary

- `setActiveTools()` only controls the active set. Registered deferred/codemode tools remain nested-callable. Moreover, a nonempty `tools` allowlist containing no `mcp__…` entries deliberately exempts MCP names from filtering; upstream tests explicitly expect MCP tools to remain with such `--tools` selections. Use an explicit, verified registered/callable inventory and exclusions, not “the model was only shown read.” [allowlist-init] [allowlist] [callability] [test-mcp-allowlist]
- Hiding tools does not disable their MCP server: startup connects every server with `enabled !== false`, independently of exposure. Connection starts a stdio process or HTTP initialization/discovery **before any tool-call approval**, including servers whose tools are hidden. Stdio inherits the process environment by default; the coding-agent transport constructor does not turn inheritance off. MCP header/env `!command` resolution is another host-shell path outside tool hooks. [mcp-enabled] [mcp-startup] [mcp-runtime] [mcp-transport] [stdio-start] [config-command]
- SDK defaults are not equivalent to CLI trust prompting: `createAgentSession()` creates ordinary settings and calls `DefaultResourceLoader.reload()` without a trust resolver; settings default to `projectTrusted: true`. CLI has a separate trust flow, but reads `sessionDir` before it. Context files load independently of trust unless disabled. Supply an owned loader/settings/session store; do not infer SDK isolation from CLI `--no-approve`. [sdk-startup] [settings-trust] [resources] [cli-session-dir] [security-trust]

## 2. Concrete gateway and fail-open behaviors

### Inputs: validation happens before mutable handlers

`tool_call` input is the validated argument object. Handlers run in order on that shared object; the pipeline subsequently executes it **without another schema check**. A late handler can change a path/command after an earlier approval or substitute a schema-invalid value. Replacing the event's `input` property is not the documented in-place patch contract. The behavior is deliberate, documented, and tested upstream; the probe changed a required string to number `17` and the tool successfully received `17`. [tool-pipeline] [tool-call-runner] [mutation-contract] [test-mutation]

Consequences for Loom: trust and fix the handler order; validate/authorize the final execution payload at the owned operations/tool boundary, including any prefix or `spawnHook` rewrite. Do not treat approval of an earlier object or display string as approval of every downstream rewrite. The built-in shell applies its prefix and spawn hook **inside execute**, after the generic call gate. [shell-rewrite]

### Outputs: a throwing redactor fails open

The extension runner catches `tool_result` exceptions, emits an extension error, and continues. With no successful patch, it returns `undefined`, preserving the original result. This differs from an exception in the lower-level `afterToolCall` callback itself, which the agent core converts to an error result: the extension runner normally swallows it first. The probe returned original text `PRIVATE` and `isError:false` after the redactor threw. Replacing `content` drops stale `structuredContent`, but a redactor must deliberately return its safe replacement; an exception is not denial. [result-runner] [tool-finalize] [session-after-hook]

Also, `tool_execution_update` partials are emitted during execution, before the final result hook; custom subscribers, UI and persistence of raw/truncated-output files need their own policy. Final-hook redaction cannot retract bytes already streamed or files already written. Codemode/MCP explicitly spill full output to host temp files. [tool-finalize] [codemode-output] [mcp-output]

### `terminate` is not a session-wide kill switch

At top level, termination is decided **after the batch** and only when **every** finalized result has `terminate:true`. One blocked terminating call does not stop an allowed sibling; parallel preflights run before their executions, and an actual abort does prevent prepared tools from starting. Nested calls return an outcome, with no automatic termination propagation; codemode converts a denied nested call into a catchable script error and does not inspect `terminate`. Probe: catch a nested `{block:true,terminate:true}`, then successfully call the same tool with permitted input. Use a durable adapter denial/abort state if a policy event must end the whole Loom task. [tool-batches] [tool-pipeline] [nested-dispatch] [codemode-script-value] [test-preflight-abort]

## 3. Cancellation, process trees and “settled”

| Mechanism | What is established |
|---|---|
| Agent tool cancellation | Pipeline checks abort around preflight and passes the signal to execute; it does not forcibly preempt arbitrary tool code or undo effects. Probe: a tool aborts its signal, ignores it, performs a delayed effect and returns success. `write`/`edit` keep their in-process file queue held until outstanding I/O settles and check abort after writes; an error/abort therefore does **not** imply unchanged files. [tool-pipeline] [tool-finalize] [write-cancel] [edit-cancel] |
| Nested/custom tools | Parent signal is a default, not mandatory confinement. Trusted tool code can override it or start unawaited work. Nested-call records cap at 256 calls, 8 KiB per argument record and 32 KiB total arguments; excess is omitted/marked incomplete while usage continues accumulating. They are neither a complete durable audit nor a resource limiter. [tool-context] [nested-record] [nested-runner] |
| Codemode finish/abort/timeout | Aborts pending host-call controllers, clears the pending set, stops the VM and resolves; it does **not** await the host calls' promises. Probe: an unawaited tool observed abort, codemode returned, and the tool produced a later effect anyway. Default coding-agent script timeout is infinite unless source specifies one; memory cap is 256 MiB. Earlier effects are never rolled back. [sandbox-cancel] [codemode-tools] [codemode-errors] |
| Built-in Bash/PowerShell and local user Bash | Shared local shell backend uses a detached POSIX process group; abort/timeout kills that group with SIGKILL (Windows uses taskkill). **Not an OS containment boundary:** Linux probe launched a `setsid` child with closed inherited stdio; it survived parent Bash cancellation and wrote its isolated marker. On ordinary completion the shell PID is untracked; cancellation is not an inventory of all descendants. [shell-process] [kill-tree] [powershell-backend] |
| Built-in grep/find | Direct subprocesses use child-level kill, not the Bash process-group backend. **Concrete grep cancellation race:** it checks abort initially, awaits helper resolution and filesystem `isDirectory`, then spawns `rg` and only then attaches an abort listener without checking current abort state. Probe aborted during the awaited directory check: the isolated fake `rg` still started and the grep result was successful. `find` has explicit post-await checks around helper resolution; do not generalize the grep-specific race to it. [grep-ops] [grep-finish] [find-ops] |
| Extension `pi.exec()` | Spawns before checking an already-aborted signal; abort/timeout sends SIGTERM only to the direct process, not a detached group. The five-second escalation tests `proc.killed` (signal sent), not confirmed process exit. Probe: direct parent was terminated, its child survived, and result was `{code:0,killed:true}` because null exit status is mapped to zero. Do not classify success from `code` alone or rely on this helper for process-tree cleanup. [exec-process] |
| MCP cancellation | Client abort/timeout rejects the local request and sends `notifications/cancelled`; it does not prove the server stopped or rolled back an external effect. Stdio transport close separately uses stdin-close, SIGTERM and SIGKILL process-group cleanup. This is cooperative request cancellation plus shutdown cleanup, not per-call transactional cancellation. [mcp-cancel] [mcp-request] [stdio-close] |
| Session abort versus user Bash | `session.abort()` aborts the agent/retry/compaction/summary and waits for idle; it does not call `abortBash()`. User Bash has separate controllers and `abortBash()`. A Loom cancel handler using only `abort()` misses that execution path. [session-abort] [sdk-bash] [abort-bash] |

### Settlement is a continuation boundary, not a verified-success transaction

- `emitBoundary()` catches a `turn_end`/`agent_before_settle` handler exception and reports it, retaining preceding shared mutations. It rebuilds the preview and can still return `valid:true, continue:false`. If proposed entries remain invalid, it drops them and returns `valid:false, entries:[], continue:false`. A later handler may replace entries or reset continuation. **Throwing “verification failed” does not veto settlement.** The first case was reproduced against the published runner; upstream tests also preserve a mutation made before a throwing handler. [boundary-runner] [test-boundaries]
- The session commits returned drafts and only continues if requested/queued **and** there is runnable context. A naked `continue:true` on a final assistant response is insufficient: `canContinue` can be false, causing an error notification and settlement. Aborting during the hook suppresses continuation. [boundary-context] [before-settle]
- The run's `finally` emits `agent_settled`, including aborted/failed runs; its payload is an `aborted` flag, not a verifier success verdict. The event means lifecycle quiescence for Pi, not “Loom checks passed,” and does not establish absence of outstanding external effects. [session-run] [settled-event] [sandbox-cancel]

**Required adapter invariant:** Loom owns a separate completion state and fresh verification evidence. Missing/throwing/cancelled/timed-out verification must leave that state unverified/failed regardless of Pi's `agent_settled` event or a resolved `prompt()` promise. A hook may request corrective continuation, but the outer adapter must independently refuse completion. This is a recommendation derived from the failure semantics above, not an upstream built-in guarantee.

## 5. Conditional no-fork recommendation

**Proceed without a fork if Loom trusts its own adapter, Pi runtime, extension/provider/tool implementations and configured MCP servers**, and treats model text/repository content as untrusted data. Keep executable resources host-owned; use explicit startup inputs and an owned loader instead of ambient project autoload. Disable codemode `models` or separately own/mediate that runtime. Enforce policy in trusted semantic tools/operations as well as call hooks, gate UI/RPC/SDK Bash consistently, handle result-hook errors conservatively, and make Loom completion conditional on its own verifier and tracked work inventory. These use existing seams; the source above establishes their availability, not an implemented or tested Loom integration. [sdk-startup] [wrapper] [shell-rewrite] [codemode-default] [user-bash-runner] [before-settle]

**Do not approve a hooks-only architecture if the trust boundary includes hostile extensions, arbitrary host shell commands, arbitrary MCP servers, or a requirement that cancellation guarantee no further effects.** Run the entire Pi process and its descendants inside a real restricted OS/container/VM boundary, keep credentials/egress outside or narrowly mediated, and use an external supervisor capable of terminating the execution domain. Tool-backend isolation alone leaves startup/extensions/model callbacks on the host. Pi's own security guidance makes the same distinction. A fork adding more hooks would improve observability or contracts, but would not turn same-process malicious Node code into a sandbox. [security]

If the product requirement is specifically “Pi itself must reject settlement when a hook throws” or “every codemode model request must emit tool hooks,” v1.3.0 does not satisfy it. Either retain the independent outer boundary described here, disable the uncovered channel, or obtain an upstream contract change; do not silently call the existing contract fail-closed. [boundary-runner] [codemode-models]
